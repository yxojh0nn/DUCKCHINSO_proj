## 2. 로그인 방식 전체

```
            ┌ 구글 · 애플 ─────────── Supabase 기본 제공자 (signInWithOAuth)
회원 로그인 ┼ 네이버 · 카카오 ─────── 서버 함수 social-login → 일회용 로그인 토큰
            └ 아이디 + 비밀번호 ──── 서버 함수 login-id     → 일회용 로그인 토큰
비회원       ── 익명 로그인 (지금과 같음)
```

- 네이버·카카오와 아이디 로그인은 같은 방식으로 세션을 만든다: 서버 함수가 본인 확인을 끝내면 Supabase 관리자 API로 **일회용 로그인 토큰**(`generateLink` magiclink의 `token_hash`)을 만들고, 앱이 `verifyOtp`로 세션을 받는다. 이메일 인증 링크와 같은 원리라 별도 세션 체계를 만들지 않는다.
- 같은 이메일로 여러 방식으로 가입한 경우(결정: 자동으로 합치지 않음): Supabase 기본 제공자(구글·애플)끼리는 인증된 같은 이메일이면 Supabase가 한 계정으로 묶는다. 네이버 계정은 **자동으로 묶지 않는다** — 이미 같은 이메일의 계정이 있으면(`email_taken`) "이미 다른 방법으로 가입한 이메일이에요. 그 방법으로 로그인해 주세요"를 보여 준다(남의 계정에 붙는 사고 방지).

## 3. 구글·카카오·애플 설정 (사용자 작업 + 확인할 것)

| 서비스 | 할 일 | 주의 |
| --- | --- | --- |
| 구글 | Google Cloud에서 OAuth 클라이언트(웹) 생성 → Supabase > Authentication > Providers > Google에 ID·Secret | 승인된 리디렉션 URI: `https://<프로젝트>.supabase.co/auth/v1/callback` |
| 카카오 | Kakao Developers 앱 생성 → 카카오 로그인 켜기 → Redirect URI `https://<프로젝트>.supabase.co/functions/v1/social-login` → REST API 키·(Client Secret)·Admin 키를 서버 함수 비밀값으로. **Supabase Kakao 제공자는 켜지 않는다** | 결정(2026-11-06): 이메일을 받지 않고 **카카오 회원번호**로 가입·로그인 → 비즈 앱 전환 불필요. 탈퇴 연결 끊기에 **Admin 키** 필요 |
| 애플 | Apple Developer에서 App ID에 Sign in with Apple 켜기, Services ID, 키(.p8) 발급 → Supabase Apple 제공자 | Supabase에 넣는 client secret(JWT)은 **최대 6개월마다 다시 만들어야 한다**. 만료되면 애플 로그인이 멈춘다 → 운영 일정에 등록 |
| 공통 | Supabase > Authentication > URL Configuration의 Redirect URLs에 웹 주소(`https://duckchinso.com/auth/callback**`)와 앱 스킴(`com.duckchinso.app://auth/callback`) | 앱 ID가 바뀌면 스킴도 바뀐다 |

키 값은 Supabase 대시보드와 서버 함수 비밀값(`supabase secrets set`)에만 넣는다. 저장소·채팅에 붙여 넣지 않는다.

## 4. 네이버·카카오 로그인 (서버 함수 `social-login`)

```
앱/웹 ──① social-login?provider=naver|kakao&to=app|<웹 주소> ──▶ 서명한 state + nonce 쿠키 ──▶ 네이버·카카오 로그인 화면
제공자 ──② code, state ──▶ social-login (GET)
social-login: ③ state 서명·만료·쿠키 nonce 확인 → ④ code로 토큰 받기 → ⑤ 회원 식별값 조회 (네이버: id·email, 카카오: 회원번호)
              → ⑥ 식별값 HMAC으로 기존 계정 찾기, 없으면 계정 생성 → ⑦ 일회용 로그인 토큰 생성
              ──⑧ 302 ──▶ <웹 또는 앱 스킴>/auth/callback#token_hash=…   (실패: #error=코드)
앱/웹 /auth/callback ── verifyOtp(token_hash) ──▶ 세션
```

- 코드: `supabase/functions/social-login`, `_shared/providers.ts`(제공자별 주소·연결 끊기). 토큰은 주소의 `#` 뒤에 실어 서버 로그에 남지 않게 하고, 앱이 받자마자 주소창에서 지운다.
- **카카오(결정 2026-11-06)**: 카카오 이메일이 아니라 **카카오 회원번호**로 계정을 찾는다. 이메일 동의 항목·비즈 앱이 필요 없다. Supabase 계정에는 이메일 칸이 필요해서 `k<무작위>@kakao.noemail.duckchinso.com`(2026-11-10 이전 계정은 `…duckchinso.app`) 자리 채움 주소를 넣는다(회원번호를 넣지 않는다). 이 주소로는 메일을 보내지 않는다(`_shared/mail.ts`) → 카카오 회원은 문의 답변을 앱의 운영팀 대화방에서만 받는다.
- **로그인 CSRF 방지**: state 서명(10분)에 더해, 시작한 브라우저에만 nonce 쿠키를 심고 돌아왔을 때 맞춘다.

- **state**: 서버 함수가 서명(HMAC)한 값에 "제공자·돌아갈 곳(앱 또는 `SITE_ORIGINS`에 있는 웹 주소)·nonce·만료"를 담는다. 10분 지나거나 서명이 틀리면 거절.
- **이메일 동의 필수**: 네이버 동의 항목에서 이메일을 필수로 둔다. 이메일이 없으면 가입을 막는다(문의 답변·계정 찾기에 필요).
- **계정 찾기 기준은 네이버 고유 id**: 이메일은 사용자가 네이버에서 바꿀 수 있으므로 기준으로 쓰지 않는다. `external_ids`에 식별값의 HMAC(6장), 암호문, 사용자 id를 저장한다.
- **토큰 보관**: 탈퇴 때 네이버 연동 해제에 refresh token이 필요하므로 암호화해서 저장한다(6장).
- 비밀값: `NAVER_CLIENT_ID`·`NAVER_CLIENT_SECRET`, `KAKAO_REST_KEY`·`KAKAO_CLIENT_SECRET`(켰을 때)·`KAKAO_ADMIN_KEY`, `SITE_ORIGINS`, `LOGIN_STATE_KEY` (배포 가이드 3장).
- 앱에서는 구글처럼 시스템 브라우저로 열고, ⑧의 앱 스킴 딥링크로 돌아온다. `useNativeAuthReturn`이 `code`와 `#token_hash`·`#error`를 모두 처리한다.

## 5. 이메일 가입 → 별도 아이디

### 흐름

```
① 아이디 입력 → [중복 확인] (login-id check_id)
② 이메일 입력 → [인증] → 메일로 인증 코드 (login-id email_code, 영문·숫자 6자리, 5분, 다시 보내기 가능)
③ 이메일 아래 코드 입력 → [확인] (login-id email_verify) → 인증 완료 표(30분, 서명) + 완료 팝업
④ 비밀번호 · 약관 동의 → 가입 (login-id signup: 표 확인 → 계정 생성 → 아이디 HMAC·암호문 저장) → 바로 로그인
⑤ 이후 로그인: 아이디 + 비밀번호
```

- 이메일은 인증 수단, 아이디는 로그인 수단이다. 메일 **링크**는 가입한 브라우저에서 열어야 이어져서(PKCE) 쓰지 않고, 어느 기기에서 메일을 봐도 되는 **코드**로 인증한다.
- 코드 메일은 Supabase 템플릿이 아니라 Resend로 직접 보낸다. Supabase 코드는 숫자뿐이고 가입 전 계정을 먼저 만든다. `RESEND_API_KEY`·`MAIL_FROM`이 없으면 가입할 수 없다.
- 코드는 HMAC으로만 저장한다(`email_codes`). 코드 하나당 5번까지 입력, 이메일당 10분에 5번·IP당 20번 발송, 중복 확인은 IP당 10분에 30번.
- 이미 가입된 이메일이면 코드 대신 안내 메일을 보내고 화면 응답은 같다(가입 여부를 알려 주지 않는다).
- "아이디 만들기" 화면(`login-id` set)은 아이디 없이 가입한 예전 계정용으로 남겨 둔다.

- 아이디는 **가입한 사람만 쓰는 로그인용**이다. 다른 사용자에게 보이는 이름은 지금처럼 닉네임이다. 아이디를 공개하면 로그인 정보의 절반이 드러나므로 프로필·채팅·글 어디에도 보여 주지 않는다. MY > 내 정보에서 본인만 본다.
- 아이디 규칙(결정): 영문 소문자로 시작, 영문 소문자·숫자·밑줄 4~20자. 대소문자 구분 없음(소문자로 저장). 아이디는 남에게 보이지 않으므로 운영용 단어·금칙어 검사는 하지 않는다.
- 이메일 형태(`@` 포함)는 아이디로 받지 않는다.
- ②에서 창을 닫아 아이디를 못 만든 사람, 아이디 도입 전에 가입한 계정(결정 4): 로그인 화면의 아이디 칸에 **이메일을 넣으면 이메일 로그인**으로 처리하고, 로그인 직후 아이디 만들기 화면으로 보낸다. 기존 계정이 모두 아이디를 만들면 이 처리를 지운다(`MemberLogin.tsx`의 `shortcut:`).

### 아이디 로그인 (서버 함수 `login-id`)

1. 아이디 → HMAC 계산 → `login_ids`에서 사용자 찾기
2. DB 함수 `check_login(id_hmac, pw)`: `auth.users`의 bcrypt 해시와 비교(`extensions.crypt`)해 사용자 id를 돌려준다. 서비스 키로만 부를 수 있다. 없는 아이디도 bcrypt를 한 번 돌린다
   - 서버 함수에서 Supabase `signInWithPassword`를 부르지 않는 이유: 모든 요청이 서버 함수의 IP 하나로 가서 Supabase 로그인 횟수 제한(IP당)에 금방 걸린다
3. 맞으면 일회용 로그인 토큰 → 앱이 `verifyOtp`로 세션
4. **실패 횟수 제한**: 같은 아이디 10분에 5번, 같은 IP 10분에 20번 실패하면 잠시 막는다(`login_attempts`에 아이디·IP의 HMAC만 기록, `run_maintenance`가 하루 지난 기록 삭제)
5. 아이디가 없거나 비밀번호가 틀려도 같은 문구("아이디 또는 비밀번호가 올바르지 않습니다")와 비슷한 응답 시간으로 답한다(아이디 존재 여부를 알려 주지 않게)

이메일을 앱에 돌려주지 않는 것이 핵심이다. 아이디로 이메일을 조회해 앱이 직접 `signInWithPassword`를 부르게 하면 아이디만 알면 남의 이메일을 알아낼 수 있다.

### 아이디·비밀번호 찾기

| 기능 | 방법 |
| --- | --- |
| 아이디 찾기 | `/login/find`: 이메일 입력 → 그 이메일로 아이디를 메일 발송(화면에는 "가입된 이메일이면 메일을 보냈어요"만, IP당 10분에 5번). **Resend 연결 필요** — 없으면 "준비 중" 안내 |
| 비밀번호 재설정 | `/login/find`: 가입한 이메일 입력 → Supabase 재설정 메일 → 링크(`/auth/callback?next=password`) → 새 비밀번호 화면(`/my/password`). MY > 내 정보에서도 바꿀 수 있다 |

## 6. 개인정보 암호화 구조

### 원칙

1. **비밀번호는 복호화할 수 없게 저장한다(일방향 해시).** 법(안전성 확보조치 기준)도 일방향 암호화를 요구한다. 복호화할 수 있으면 키가 새는 순간 모든 비밀번호가 샌다. Supabase가 bcrypt로 저장하고, 우리는 비밀번호 원문을 어디에도 남기지 않는다(로그 포함).
2. **복호화가 필요한 값은 앱 계층에서 AES-256-GCM으로 암호화**하고, 키는 DB가 아닌 서버 함수 비밀값에만 둔다. DB가 통째로 유출돼도 키가 없으면 읽을 수 없다.
3. **찾기용 값은 HMAC(블라인드 인덱스)으로 따로 둔다.** 암호문은 매번 달라서 검색이 안 된다. 아이디 중복 확인·로그인은 HMAC으로 찾고, 화면에 보여 줄 때만 복호화한다.
4. **암호화·복호화는 서버 함수에서만** 한다. 앱(브라우저)과 DB 함수는 키를 모른다.
5. 원본을 복사해 두지 않는다. 이메일은 `auth.users`에만 둔다.

### 항목별

| 항목 | 저장 위치 | 방식 | 복호화 | 이유 |
| --- | --- | --- | --- | --- |
| 비밀번호 | `auth.users.encrypted_password` | bcrypt 해시 (Supabase) | **불가** | 법정 일방향 암호화. 확인은 해시 비교로만 |
| 이메일 | `auth.users.email` | Supabase 관리. 저장 장치 암호화(AES-256)와 전송 암호화(TLS) | Supabase Auth가 인증 메일에 사용 | 인증 메일·비밀번호 재설정에 원문이 필요하고 Auth가 직접 읽는다. 우리 표에는 복사하지 않는다 |
| 로그인 아이디 | `login_ids` | `id_hmac`(HMAC-SHA256, 찾기용) + `id_enc`(AES-256-GCM, 보여 주기용) | 본인 MY 화면, 아이디 찾기 메일 | 요청 사항. 찾기는 HMAC, 표시만 복호화 |
| 네이버 id·카카오 회원번호 | `external_ids` | `subject_hmac`(찾기용) + `subject_enc`(AES) | 탈퇴 때만(카카오 연결 끊기에 회원번호 필요) | 계정 찾기 |
| 애플·네이버 refresh token | `provider_tokens` | AES-256-GCM | 탈퇴 처리 때만 | 탈퇴 시 연결 해제에 필요. 다른 용도로 쓰지 않는다 |
| 닉네임·소개·글·채팅 | `public.*` | 암호화하지 않음 | — | 다른 사용자에게 보여 주는 공개 정보. 저장 장치 암호화만 |
| 가려진 채팅 원문 | `public.message_originals` | 암호화하지 않음(운영자 함수만 읽음) | — | 신고 처리. 2차에서 AES로 바꿀지 검토 |

### 암호문 형식과 키

```
id_enc = "v1:" + base64(iv 12바이트) + ":" + base64(암호문 + 인증 태그)
AAD(추가 인증 데이터) = 사용자 id + ":" + 항목 이름   ← 다른 행의 암호문을 옮겨 붙이면 복호화 실패
id_hmac = HMAC-SHA256(PII_HMAC_KEY, "login:" + lower(아이디))   ← 용도(login·naver·kakao·ip)를 앞에 붙여 서로 다른 값이 된다
```

| 키 | 용도 | 보관 |
| --- | --- | --- |
| `PII_ENC_KEY` (32바이트) | AES-256-GCM 암호화·복호화 | 서버 함수 비밀값 + 비밀번호 관리자에 백업. **잃으면 아이디·토큰을 복구할 수 없다** |
| `PII_HMAC_KEY` (32바이트) | 아이디·네이버 id 찾기용 HMAC | 같은 방식. 암호화 키와 따로 둔다 |
| `LOGIN_STATE_KEY` | 네이버 state 서명 | 같은 방식 |

- 키는 사용자가 만들어 넣는다: `openssl rand -base64 32` → `npx supabase secrets set PII_ENC_KEY=…`. 채팅·저장소에 붙여 넣지 않는다.
- **키 교체**: 새 키를 `v2`로 추가 → 정기 작업이 `v1` 암호문을 복호화해 `v2`로 다시 암호화 → 끝나면 `v1` 삭제. HMAC 키 교체는 아이디 원문(복호화)으로 HMAC을 다시 계산한다.
- 서버 함수 공통 모듈 `_shared/crypto.ts`(Web Crypto `AES-GCM`, `HMAC`): `encrypt(userId, field, text)`, `decrypt(...)`, `blindIndex(scope, text)`, `signState`·`verifyState`. 테스트 `crypto.test.ts`(`pnpm test`).

### 표 구조 (마이그레이션 `20261106000011_login_ids.sql`)

| 표·함수 | 내용 |
| --- | --- |
| `login_ids(user_id, id_hmac unique, id_enc)` | 로그인 아이디 |
| `external_ids(provider naver·kakao, subject_hmac, subject_enc, user_id)` | 간편 로그인 식별값. 기본 키 (provider, subject_hmac) |
| `provider_tokens(user_id, provider apple·naver, refresh_enc)` | 탈퇴 때 연결 해제용 |
| `login_attempts(key, at)` | 아이디 로그인 실패·아이디 찾기 요청 기록 |
| `my_login()` | 앱용: 간편 로그인 종류, 아이디 유무, 아이디 만들기가 필요한지 |
| `check_login(id_hmac, pw)` · `login_id_by_email(email)` | 서비스 키 전용 |

- 처음 설계의 `private` 스키마 대신 `public`에 두고 **RLS를 켠 채 정책을 두지 않으며 anon·authenticated 권한을 모두 뺐다**(`message_originals`와 같은 방식). `private` 스키마는 API로 노출해야 서버 함수가 쓸 수 있어서다. 앱이 이 표를 읽거나 쓰면 permission denied (DB 테스트로 확인).
- 탈퇴(`auth.users` 삭제) 시 `on delete cascade`로 모두 지워진다.
- `handle_new_user`: 닉네임 기본값을 `덕친0000`으로.

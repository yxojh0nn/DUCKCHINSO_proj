> 리포트 원문은 공개 저장소에 올리지 않는다(공격 재현 명령 포함). 이 문서는 **조치 설계**만 담는다.

## 0. 한눈에

- High 이상 없음. 관리자 쓰기, 남의 데이터 수정·삭제, 남의 DM 열람, 스키마 전환은 모두 RLS에서 막혔다.
- Medium 대부분은 **"이메일 없는 비회원(익명 로그인)도 `authenticated` 역할"** 이라는 한 가지 원인에서 나온다. 정책·RPC에 회원 여부 조건 하나를 넣으면 절반 이상 해결된다.
- 코드와 대조하니 리포트 권고를 그대로 적용하면 **깨지는 화면이 3곳** 있다(아래 ⚠). 그래서 그대로 따르지 않고 우회 설계를 함께 적는다.

## 3. 설계

### 진행 상황 (2026-11-11)

**1단계 배포 완료 (2026-11-11).** 운영 DB 21·22 적용, main `55689cc` Vercel 배포, Supabase CAPTCHA 켬. `supabase/migrations/20261111000021_security_guest_scope.sql`, `20261111000022_own_edit.sql`(본인 글·댓글만 수정) + 클라이언트 수정 + Turnstile 위젯(`src/components/Captcha.tsx`) + CSP Report-Only. `pnpm test`(DB 권한 검증 포함)·`pnpm build` 통과, 데모 모드에서 비회원 화면 확인.

남은 일 (순서대로):
1. 운영 DB에 마이그레이션 21·22 적용 → **같은 때 웹 배포** (21 적용 후 옛 빌드는 내 프로필을 `select('*')`로 읽어 실패한다. 반대로 새 빌드는 21 없이 `my_profile`이 없어 실패 → 둘을 붙여서)
2. 6장 확인 SQL 5번으로 닉네임 제약 위반 행 정리 → `alter table public.profiles validate constraint profiles_nickname_chars;`
3. Cloudflare Turnstile 위젯 만들기(허용 호스트: duckchinso.com, localhost) → 사이트 키를 Vercel 환경변수 `VITE_TURNSTILE_SITE_KEY`에 넣고 재배포 → Supabase Auth > Attack Protection에 비밀 키로 CAPTCHA 켜기 + Rate Limits
4. CSP Report-Only 1주 관찰 후 `Content-Security-Policy`로 전환
5. `public/.well-known/security.txt` — **운영 연락 메일 주소가 정해지면** 추가 (저장소에 공개 연락처가 없음)

확인으로 닫은 항목: `answer-inquiry` 메일은 고정 문구 평문이라 사용자 입력이 들어가지 않음(L5 메일 위험 없음). `login-id` 인증코드는 유효시간·코드당 시도 횟수·이메일/IP별 발송 한도가 있음.

### 3-0. 공통 헬퍼: `is_member()`

구현은 JWT 클레임 대신 `profiles.is_guest`를 본다. 기존 `submit_ticket_tip`(마이그 15)과 같은 기준이고, 가입 트리거가 `auth.users.is_anonymous`로 채운다. 비회원→회원 전환은 "별개 계정"(보안 기획서 26행)이라 값이 어긋날 일이 없고, DB 테스트(PGlite)에서도 그대로 검증된다. 함수 안에서 회원 검사가 필요한 곳은 `require_member()`(아니면 `members_only` 예외).

### 3-2a. M5 완료 방안 — Supabase 안에서

M5의 원인: 아이디 로그인(`login-id` 함수)은 자체 시도 제한이 있지만, 같은 계정을 **Supabase Auth 기본 엔드포인트 `/auth/v1/token?grant_type=password`** 로 직접 두드리면 그 제한을 거치지 않는다. 앱 코드가 아니라 Auth 서버가 받는 요청이라, 막는 곳도 Auth 설정이다.

| 순서 | 위치 (대시보드) | 설정 | 효과 |
| --- | --- | --- | --- |
| 1 | Authentication > **Rate Limits** | "Sign-ups and sign-ins" (IP당 5분 단위)를 기본값보다 낮게(예: 5분에 10회), "Anonymous users" 시간당 IP당 30, "Token refreshes"는 기본 유지 | 같은 IP에서 비밀번호 대입·익명 가입 반복이 429로 끊긴다 |
| 2 | Authentication > **Attack Protection > CAPTCHA** | Turnstile 선택, 비밀 키 입력 → 켜기 | 비밀번호 로그인·가입·익명 로그인·OTP/재설정 메일 요청마다 캡차 토큰 필요 → 스크립트 대입 자체가 불가. **사이트 키를 넣은 웹 빌드를 먼저 배포한 뒤** 켠다 |
| 3 | Authentication > Attack Protection > **Leaked password protection** (Pro) | 켜기 | 유출된 비밀번호로 가입·변경 차단(대입 성공률 하락) |
| 4 | Authentication > Providers > Email | "Secure password change"·최소 길이 8 이상 확인 | 약한 비밀번호 제거 |
| 5 | (선택) 이메일 비밀번호 로그인 경로 닫기 | `MemberLogin`의 `@` 입력 → `signInEmail` 분기(코드에 `shortcut:` 표시)는 아이디가 없던 옛 계정용. 모든 이메일 계정이 아이디를 만들면 분기를 지우고, 그 뒤엔 Auth 쪽 password grant 를 써야 할 이유가 없다 | 공격 표면 자체 제거. 단 Supabase는 password grant 만 따로 끄는 스위치가 없어 1·2는 계속 필요 |

확인: 설정 후 같은 IP에서 잘못된 비밀번호로 `/auth/v1/token?grant_type=password` 를 15회 보내 429가 나오는지(리포트 M5 표와 같은 방법), 캡차 켠 뒤 토큰 없이 보내면 `captcha_failed` 400이 나오는지.

### 3-3. 2단계 설계 — 마이그레이션 24 `audit_and_integrity` (M7·M8·L7·I2)

> 번호: 마이그레이션 22는 "본인 글·댓글만 수정"(`own_edit`, 구현 완료)에 썼다. 2단계는 24, 3단계는 25. 23은 M1 마무리(`guest_profile_scope`).

**M7 출처(`source`) 위조 방지**
- check 제약은 **이미 있다**(`artists.source in ('admin','musicbrainz')`, `concerts.source in ('admin','kopis')`, init.sql 126·175행). 남은 건 "누가 넣었나"를 클라이언트가 고를 수 없게 하는 것.
- `before insert or update` 트리거 `force_source()` (artists·concerts): `auth.uid() is not null` 이면(=앱에서 로그인 사용자가 보낸 요청) `new.source := 'admin'`. 수집 함수(`sync-artists`·`sync-concerts`·`import-concert`)는 service_role 키라 `auth.uid()`가 null → 보낸 값 유지.
- `supabaseApi.ts` 434·540행 `source: 'admin'` 제거(보내도 트리거가 덮지만 계약을 분명히).
- 테스트: 운영자가 `source='musicbrainz'`로 넣어도 `admin`으로 저장.

**M8 감사 추적**
- `artists`·`concerts`에 `created_by uuid references auth.users on delete set null default auth.uid()`, `updated_by uuid`, `updated_at`(concerts는 이미 있음) 추가. `before update` 트리거가 `updated_by := auth.uid()`, `updated_at := now()`.
- `admin_audit_log (id bigint identity, at timestamptz default now(), actor uuid, table_name text, row_id text, action text check in ('insert','update','delete'), before jsonb, after jsonb)`.
  - `after insert or update or delete` 트리거 `audit_row()` (security definer): `auth.uid()`가 있을 때만 기록(수집 함수의 대량 변경은 제외 — 양이 많고 주체가 시스템이라 의미 없음).
  - 대상 표: artists, concerts, concert_artists, ticket_links, concert_schedules, banned_words, allowed_words, jpop_promoters, sanctions, admins.
  - **append-only**: authenticated·anon 에 GRANT 없음, 읽기는 `admin_audit(limit, offset)` RPC(운영자만). service_role 도 UPDATE/DELETE 를 revoke 해 대시보드 실수로도 안 지워지게.
  - 보관: 1년 지난 행은 `run_maintenance()`에서 삭제(개인정보 최소 보관과 맞춤, 처리방침에 "운영 기록 1년").
- 운영자 화면 "사용자 상세"처럼 "아티스트 상세"에 "마지막 수정: 닉네임 · 날짜" 한 줄(선택).

**L7 내 메시지 삭제**
- `messages`에 `deleted_at timestamptz`. `delete_my_message(m uuid)` RPC: `sender_id = auth.uid()` 이고 `kind in ('text','image')`일 때 `body := ''`, `image_path := null`, `deleted_at := now()`.
- 하드 삭제를 안 하는 이유: 상대가 이미 신고했다면 `reports.content_snapshot`에 원문이 남아 있지만, 신고 전 삭제로 증거를 지우는 걸 막으려면 금칙어 원문 표(`message_originals`)처럼 운영자만 보는 원문 보관이 필요 → `message_originals`에 삭제 전 본문을 복사(30일 보관 후 정리).
- 이미지 파일: `chat-media`에서 보낸 사람 경로 삭제 정책(`(storage.foldername(name))[2] = auth.uid()::text`) 추가, 앱이 RPC 성공 후 Storage 삭제 호출.
- 화면: 내 말풍선 길게 누르기 → "삭제" → "삭제된 메시지예요" 표시. 목록 마지막 메시지도 같은 문구.

**I2 동의 시각·온보딩 위조 방지**
- `revoke update (community_agreed_at, profile_setup_done) on profiles from authenticated`.
- `agree_community()` RPC: `consents`에 (community, 현재 버전, true) 행을 넣고 같은 트랜잭션에서 `community_agreed_at = now()`. 시각을 클라이언트가 못 정한다.

### 3-4. 3단계 설계 — 마이그레이션 25 `admin_rpc` (L1·L2·L4)

**L1 완료 방안 — "RLS 하나에만 기대는 구조"를 두 겹으로**

지금 구조: 표 권한(GRANT)은 넓게 열고, 행을 거르는 건 RLS 정책뿐이다. 정책 하나를 잘못 고치면(예: `using (true)`) 바로 뚫린다. M1이 실제 사례다. 완료 기준은 **"앱이 표에 직접 쓸 일이 없는 표는 GRANT 자체가 없다"** — 그러면 정책이 틀려도 `42501 permission denied`에서 멈춘다.

| 표 | 지금 authenticated 권한 | 앱의 실제 사용 | 3단계 후 |
| --- | --- | --- | --- |
| artists | SELECT·INSERT·UPDATE·DELETE | 읽기 + 운영자 저장(`supabaseApi.ts` 548·549) | **SELECT만**. 저장은 `admin_save_artist()` |
| concerts, concert_artists, concert_schedules, ticket_links | 전체 쓰기 | 읽기 + 운영자 게시·숨김(434~443) | **SELECT만**. `admin_publish_concert()`·`admin_hide_concert()` |
| banned_words, allowed_words | 전체 | 운영자 목록·추가·삭제(561~566) | **없음**. `admin_words()`·`admin_add_word()`·`admin_delete_word()` |
| jpop_promoters | SELECT·INSERT·DELETE | 운영자 게시 때 upsert(440) | **없음**. 게시 RPC 안에서 처리 |
| kopis_inbox | SELECT | 운영자 검색 | **없음**. `admin_search_inbox()` |
| reports | SELECT·INSERT·UPDATE·DELETE | 신고 넣기(320) + 운영자 RPC | **INSERT만** (처리는 기존 `admin_resolve_report`) |
| inquiries | SELECT·INSERT | 문의 넣기 + 운영자 RPC | **INSERT만** (본인 문의 목록 화면이 없으므로) |
| sanctions | SELECT·INSERT | 앱 직접 사용 없음(기존 `admin_sanction`·`admin_user_sanctions` RPC) | **없음** |
| posts | UPDATE 전체 | 앱 직접 수정 없음(수정은 `edit_post`, 숨김은 운영자 RPC) | **UPDATE 회수** |

- RPC 공통 틀: `security definer set search_path = ''`, 첫 줄 `if not public.is_admin() then raise exception 'forbidden'; end if;`, 그리고 M8 감사 로그가 표 트리거로 자동 기록.
- 기존 운영자 RPC 12개(마이그 7·14·15·17)와 같은 패턴이라 새 구조가 아니다.
- 순서: ① RPC 추가 + 앱을 RPC로 교체해 배포 ② 하루 관찰 ③ GRANT 회수 마이그레이션 적용. ①과 ③을 한 번에 하면 배포 전 옛 앱의 운영자 화면이 바로 깨진다.
- 검증: DB 테스트에 "운영자도 표 직접 INSERT 는 permission denied, RPC 는 성공", 그리고 6장 SQL 2번 결과가 위 표의 "3단계 후" 열과 같은지.
- 남는 넓은 권한: 사용자 본인 데이터 표(favorites, user_artists, user_genres, consents, push_tokens, messages, posts, comments)는 앱이 직접 쓰는 게 자연스러워 GRANT를 유지하고, 정책은 모두 `user_id = auth.uid()` 형태라 단순하다.

**L2** 위 표의 운영자 RPC 이전이 곧 L2 완료. 화면 가드(`isAdmin` 메뉴 표시)는 그대로 두되 권한 판단은 DB만.

**L4 Realtime 채널** `sb.channel('user:' + uid)`. postgres_changes는 이미 RLS를 따르므로 기능·보안 변화는 작다. 나중에 Broadcast(입력 중 표시 등)를 쓰게 되면 그때 Realtime Authorization(private channel)과 `realtime.messages` 정책을 함께 도입.

### 3-6. D3 검토: 남의 취향 데이터 공개가 개인정보 침해가 되는가

사용자 결정: 비회원 포함 모두 볼 수 있게 하되, 특정 회원이 드러나 침해 위험이 있으면 백엔드에서 막는다.

**지금 실제로 공개되는 것** (`ProfileView.tsx`): 닉네임·소개·프로필/배너 사진 + 관심 아티스트 이름 + 장르 + 관심 공연 목록(**다가오는 공연**과 지난 공연, 날짜·공연장 포함).

| 데이터 | 단독 위험 | 다른 정보와 결합 시 | 판정 |
| --- | --- | --- | --- |
| 관심 아티스트·장르 | 음악 취향은 개인정보보호법 23조 민감정보(사상·신념, 건강, 성생활 등)가 아니다. 서비스 본질(취향 매칭)이라 공개가 기대되는 정보 | 닉네임·사진과 묶여도 "누가 무엇을 좋아한다" 이상의 피해가 작다 | **위험 낮음 → 유지** |
| 지난 관심 공연 | 과거 동선 일부 | 후기 글과 겹치면 이미 본인이 공개한 정보 | **위험 낮음 → 유지** |
| **다가오는 관심 공연** | **미래의 특정 날짜·장소에 이 사람이 있을 가능성**을 알려 준다 | 프로필·배너 사진(얼굴일 수 있음)과 결합하면 공연장 현장에서 특정 인물을 찾아갈 수 있다 → 스토킹·현장 접근 위험. 비회원은 이메일 없이 무제한 생성되던 계정(M2)이라 추적이 안 된다 | **위험 있음 → 제한** |
| 테이블 직접 읽기(`using (true)`) | — | 한 번의 요청으로 **전 회원의 취향·관심 공연을 통째로** 내려받아 `profiles`와 조인 → 대량 프로파일링, "이 공연에 갈 사람 목록" 역조회 가능 | **위험 있음 → 차단** |

**설계 (백엔드에서 특정을 막는 로직)**

1. **대량 조회 차단**: `user_artists`·`user_genres`·`favorites` 읽기 정책을 `user_id = auth.uid()`로 축소. 남의 데이터는 `profile_card(uid)` 한 사람씩만. "이 공연을 관심 등록한 사람" 같은 역조회 RPC는 만들지 않는다.
2. **`profile_card(target uuid)`** (security definer) 반환:
   - 공개 컬럼(id, nickname, bio, avatar_url, banner_url, is_guest), 관계(self/friend/sent/received/none), room_id
   - `artist_ids`, `genre_ids`: 누구에게나
   - `favorite_ids`: 지난 공연(`last_date < 오늘`)은 누구에게나, **다가오는 공연은 본인과 친구에게만**
   - `upcoming_count`: 다가오는 관심 공연 개수(숫자만) — 친구가 아니어도 "관심 공연 N개" 표시는 가능
   - 차단 관계(`is_blocked_between`)이거나 대상이 `banned`면 `not_found`
3. **화면**: `ProfileView`의 "다가오는 공연" 칸은 친구가 아니면 목록 대신 "관심 공연 N개 · 친구가 되면 볼 수 있어요" 안내.
4. 남는 한계: 게시글 작성자 임베딩으로 회원 id는 계속 보이므로 id를 모아 `profile_card`를 하나씩 부르는 수집은 가능하다. 단, 돌려받는 건 취향과 지난 공연뿐이라 위험이 낮다. `shortcut:` 호출 횟수 제한은 두지 않는다 — 수집 정황(로그상 한 계정의 대량 호출)이 보이면 `profile_card`에 호출자별 시간당 한도를 넣는다.

**결론**: 아티스트·장르·지난 공연은 변경 없이 공개 유지. **다가오는 관심 공연만 친구 공개로 바꾸고, 테이블 직접 읽기를 막는다.** 개인정보처리방침의 "공개되는 정보" 항목에 "관심 아티스트·장르·지난 관심 공연은 모든 이용자에게 공개, 다가오는 관심 공연은 친구에게만"을 적는다.

## 5. 앱 배포 시 처리 (지금은 설계만 · 출시 직전에 다시 알림)

**L8 모바일 OAuth 콜백 커스텀 스킴.** 지금 네이티브 빌드는 `com.duckchinso.app://auth/callback`을 쓴다. 커스텀 스킴은 OS가 소유권을 검증하지 않아 같은 기기의 다른 앱이 같은 스킴을 등록해 로그인 콜백(일회용 토큰)을 가로챌 수 있다. 앱이 아직 스토어에 없어서 지금은 결함이 아니다.

출시 전 할 일:
1. **Android App Links**: `public/.well-known/assetlinks.json` 배포 (패키지 `com.duckchinso.app` + Play 앱 서명 키 SHA-256 지문 — Play Console 앱 서명 페이지에서 복사). `AndroidManifest.xml` 인텐트 필터에 `https://duckchinso.com/auth/callback` + `android:autoVerify="true"`.
2. **iOS Universal Links**: `public/.well-known/apple-app-site-association`(확장자 없음, `Content-Type: application/json` 헤더를 `vercel.json`에 추가) — `appIDs: ["<TeamID>.com.duckchinso.app"]`, `paths: ["/auth/callback*"]`. Xcode Associated Domains에 `applinks:duckchinso.com`.
3. 콜백 주소를 `https://duckchinso.com/auth/callback`으로 바꾸고 Supabase Redirect URLs·구글·카카오·네이버·애플 콘솔·`social-login` 허용 목록(`to=app`)을 함께 교체. 커스텀 스킴은 허용 목록에서 제거.
4. **PKCE 확인**: Supabase 기본 경로는 이미 `flowType: 'pkce'`. 자체 `social-login`(카카오·네이버)은 서명 state + nonce 쿠키로 CSRF는 막지만 PKCE는 없다 → 일회용 토큰을 앱 링크로 넘기는 구간은 3번 전환으로 가로채기가 막히고, 추가로 앱이 만든 `code_verifier` 해시를 `state`에 넣고 토큰 교환 시 검증하는 방식을 검토.
5. 확인: 기기에서 `adb shell pm get-app-links com.duckchinso.app`이 `verified`, iOS는 메모 앱에 링크 붙여 길게 눌러 앱으로 열리는지.

이 항목은 [앱_배포_계획.md](앱_배포_계획.md) 2장 "출시를 막는 것"에도 올려 두었다.

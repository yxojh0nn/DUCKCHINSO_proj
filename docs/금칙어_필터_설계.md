# 덕친소 금칙어 필터 설계

작성일: 2026-11-05 (2026-11-06 결정 반영, 마이그레이션 10으로 구현) · 기준: Apple 심사 가이드라인 1.2(사용자 생성 콘텐츠), 커뮤니티 이용 규약, 현재 DB(글·댓글·채팅·프로필은 앱이 표에 직접 저장하고 RLS가 막는 구조)

## 1. 왜 필요한가

Apple 1.2는 사용자끼리 글·채팅을 주고받는 앱에 네 가지를 요구한다. 지금 셋은 있고 **필터만 없다.**

| 요구 | 덕친소 |
| --- | --- |
| 부적절한 내용을 거르는 방법 | **없음 → 이 문서** |
| 신고 기능과 빠른 처리 | 있음 (신고 → 운영자 화면 → 가리기·제재) |
| 사용자 차단 | 있음 |
| 운영자 연락처 | 있음 (MY > 문의) |

## 2. 결정할 원칙

1. **서버(DB)에서 거른다.** 글·댓글·채팅·프로필은 앱이 Supabase 표에 직접 쓴다. 앱 화면에서만 거르면 API를 직접 부르는 사람은 우회한다. 저장 직전 DB 트리거가 검사하면 어느 경로로 써도 같은 규칙이 적용된다.
2. **글·댓글·프로필은 거절, 채팅은 가리고 전송 (2026-11-06 결정).**
   - 글·댓글·닉네임·소개: 저장을 막고 "사용할 수 없는 표현이 들어 있어요"를 보여 준다. 어떤 단어인지는 알려 주지 않는다(우회 단어를 찾는 데 쓰이지 않게).
   - 채팅: 금칙어가 든 낱말을 같은 길이의 `*`로 바꿔 보낸다(`ㅋㅋ 씨발 뭐야` → `ㅋㅋ ** 뭐야`). 한 글자씩 띄운 욕설처럼 낱말로 못 찾으면 메시지 전체를 가린다. **원문은 `message_originals`에 따로 저장**하고 대화 당사자는 읽을 수 없다. 이 채팅이 신고되면 신고 스냅숏에 원문이 들어가 운영자가 본다. 메시지가 지워지면 원문도 같이 지워진다.
3. **목록은 운영자가 앱에서 고친다.** 배포 없이 단어를 추가·삭제한다(운영자 화면 > 데이터 > 금칙어).
4. **오탐을 막는 허용어를 같이 둔다.** 예: `시발점`(출발점), `수박씨발라`처럼 금칙어를 품은 정상 단어는 허용어 목록으로 먼저 지운 뒤 검사한다.

## 3. 검사 대상

| 표 | 칸 | 검사 시점 | 비고 |
| --- | --- | --- | --- |
| `profiles` | `nickname`, `bio` | 저장·수정 | 닉네임은 공개 식별자라 가장 엄격 |
| `posts` | `title`, `body`, `tags` | 저장 | 글 수정 기능이 생기면 수정에도 |
| `comments` | `body` | 저장 | |
| `messages` | `body` (text 종류만) | 저장 | 운영자가 보낸 운영팀 메시지(sender 없음)는 제외 |
| (제외) `inquiries` | | | 운영자만 읽는다. 욕설 신고 내용을 그대로 적어야 할 수도 있다 |
| (제외) 사진 | | | 1차는 신고로 대응. 이미지 자동 판별은 2차 검토 |

## 4. 검사 방법

```
원문 → ① 정규화 → ② 허용어 지우기 → ③ 금칙어 포함 검사 → 걸리면 'blocked_word' 오류
```

1. **정규화:** 우회 표기를 한 형태로 모은다.
   - `normalize(text, NFKC)` → 전각·호환 문자 통일, `lower()` → 영문 대소문자 통일
   - 한글·자모·영문·숫자·일본어 외 기호는 지운다 → `씨.발`, `씨-발`이 `씨발`
   - **띄어쓰기는 지우지 않는다.** 모두 지우면 `7시 발표`·`다시 발매`가 `시발`에 걸린다. 한 글자씩 띄워 쓴 것만 붙인다 → `씨 발`은 `씨발`, `7시 발표`는 그대로
   - 숫자 끼우기(`씨1발`)는 숫자를 지운 형태로도 한 번 더 검사한다(숫자가 뜻인 닉네임까지 지우지 않게 두 번 검사)
2. **허용어 지우기:** 정규화한 글에서 허용어를 먼저 빈칸으로 바꾼다.
3. **포함 검사:** `banned_words`의 단어가 하나라도 들어 있으면 거절. 짧은 단어(1~2자)는 오탐이 많아 `exact`(칸 전체가 그 단어일 때만, 닉네임용)로 둘 수 있다.

**부하:** 단어 수백 개 × 글 1건 검사는 밀리초 단위다. 지금 규모(소규모 팬 커뮤니티)에서는 캐시가 필요 없다. 단어가 수천 개를 넘거나 쓰기가 초당 수십 건이 되면 정규식 하나로 합쳐 캐시하는 방식으로 바꾼다.

## 5. 데이터

```sql
banned_words  (word text primary key, match text check (match in ('contains','exact')) default 'contains',
               category text check (category in ('abuse','sexual','hate','scam')), created_at timestamptz)
allowed_words (word text primary key, created_at timestamptz)
```

- 둘 다 운영자만 읽고 쓴다(RLS: `is_admin()`). 일반 사용자에게 목록을 보여 주지 않는다.
- 단어는 저장할 때 같은 정규화를 거쳐 넣는다(`씨 발`을 넣어도 `씨발`로 저장).
- **초기 목록 (2026-11-06 결정: 공개 데이터셋 기반):** [ZIZUN/korean-malicious-comments-dataset](https://github.com/ZIZUN/korean-malicious-comments-dataset)(MIT, 악성 5,000·정상 5,000 댓글)은 단어 목록이 아니라 문장 데이터라 그대로 넣을 수 없다. 악성 댓글에 정상 댓글보다 6배 이상 자주 나온 2~3글자 표현을 뽑고, 사람이 골라 금칙어 약 100개와 오탐을 막는 허용어 약 25개로 만들었다(마이그레이션 10의 초기 데이터). 데이터셋 원문은 저장소에 넣지 않는다. 정치인 이름, `미친`(팬덤에서 칭찬으로 씀), `개`+형용사(`개새로운`)처럼 오탐이 큰 표현은 뺐다. J-pop 커뮤니티 특성상 일본어 욕설 몇 개와, 티켓 사기 신호(선입금 계좌 유도 문구)는 오탐 위험이 커서 1차 목록에서 빼고 신고 데이터를 본 뒤 추가한다.
- 단어를 추가해도 이미 올라온 글은 다시 검사하지 않는다(신고로 처리).

## 6. 화면

| 화면 | 동작 |
| --- | --- |
| 글쓰기·댓글·채팅·닉네임·소개 | 저장 실패 시 토스트 "사용할 수 없는 표현이 들어 있어요. 고쳐서 다시 올려 주세요." 입력한 내용은 지우지 않는다 |
| 운영자 > 데이터 > 비속어 | 금칙어·허용어 목록, 추가·삭제, **문장 시험 칸**(문장을 넣으면 걸리는지와 어떤 단어에 걸렸는지 운영자에게만 표시) |
| 데모 모드 | 필터 없음 (데모에는 운영자 화면도 없다) |

`errorText`에 `blocked_word` 문구를 추가한다.

## 7. 구현 (마이그레이션 10 `20261106000010_word_filter.sql`)

1. `banned_words`·`allowed_words`(운영자만), `message_originals`(정책 없음 → 아무도 직접 못 읽음) 표
2. `norm_text(t)` 정규화, `blocked_word(t, exact_too)` 걸린 단어, `mask_text(t)` 채팅 가리기
3. 트리거 `check_banned_words`: profiles·posts·comments는 바뀐 칸만 검사해 거절(운영자가 금칙어 든 글을 가릴 때 막히지 않게), messages는 가리고 원문 저장
4. 신고 스냅숏(`fill_report_snapshot`)이 채팅 원문을 쓴다
5. `admin_test_text(t)` 운영자 시험 칸
6. 앱: 운영자 > 비속어 화면(`/admin/words`), 오류 문구 `blocked_word`, 개인정보 처리방침 표에 "가려진 채팅 원문" 줄

**DB 테스트 (`pnpm test:db`):** 금칙어·기호·띄어 쓴·숫자 끼운·자모·전각 변형 거절 · `7시 발표`·`시발점`·`등신대`·`다시 발매` 통과 · 닉네임 `exact` 거절, 소개의 `보지 마세요` 통과 · 채팅 가림과 원문 보관, 당사자 원문 열람 불가, 신고 스냅숏 원문 · 일반 사용자는 목록을 읽지도 쓰지도 못함 · 단어 정규화 저장 · 운영자가 기존 글을 가릴 수 있음.

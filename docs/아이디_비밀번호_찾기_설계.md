# 아이디·비밀번호 찾기 설계

작성일: 2026-11-11 (같은 날 개정: 비밀번호 찾기를 자체 인증코드 방식으로 변경) · 대상: 아이디 계정. 카카오·네이버·구글·Apple 계정은 각 서비스로 로그인한다.

## 1. 흐름

| 기능 | 입력 | 서버 (`login-id` 함수) | 메일 |
| --- | --- | --- | --- |
| 아이디 찾기 | 가입 이메일 | `find`: 아이디가 있으면 아이디를, **아이디 없이 가입한 계정이면 로그인 방법 안내**를 보낸다. 가입 안 된 이메일은 아무것도 보내지 않는다 | Resend |
| 비밀번호 찾기 1 | 아이디 + 가입 이메일 | `reset_code`: 그 아이디의 계정 이메일이 입력과 **같을 때만** 6자리 코드(5분) 발송 | Resend |
| 비밀번호 찾기 2 | 코드 + 새 비밀번호(확인 입력) | `reset_verify`: 아이디·이메일 재확인 → 코드 확인 → 비밀번호 변경 → **모든 기기 로그아웃** → 변경 알림 메일 | Resend |

화면 응답은 계정 존재·아이디/이메일 일치 여부와 관계없이 같다(남의 계정 확인 불가).

## 2. 보안 규칙

| 규칙 | 값 |
| --- | --- |
| 본인 확인 | 아이디 + 가입 이메일 일치 + 그 이메일로 받은 코드 (세 가지 모두) |
| 코드 | 영문 대문자·숫자 6자리(헷갈리는 0·O·1·I 제외), 5분, 1회용, 5번 틀리면 무효. DB 에는 HMAC 만 저장(`email_codes`, 가입 코드와 키 공간 분리) |
| 횟수 제한 (10분) | 코드 요청: 아이디당 5회·IP당 20회 / 코드 확인: 아이디당 5회·IP당 20회 / 아이디 찾기: IP당 5회 |
| 비밀번호 규칙 | 영문+숫자 8~72자 (가입과 같음), 서버에서 다시 검사 |
| 변경 후 | `revoke_user_sessions()`로 그 계정의 모든 세션·갱신 토큰 삭제, 가입 이메일로 "비밀번호가 바뀌었어요" 알림 |
| 로그 | 아이디·이메일·코드·비밀번호는 남기지 않음. 메일 실패는 `mail_failed <상태코드> <오류 이름> <제목>`만 |
| 로그인 API 제한 회피 | 함수 안에서 `signInWithPassword` 등 IP 제한이 걸리는 로그인 API 를 부르지 않고 관리자 API(`updateUserById`)·DB 함수만 쓴다 |

Supabase 기본 재설정 메일(링크 방식, `resetPasswordForEmail`)은 앱에서 더 이상 쓰지 않는다. 그래서 Supabase Auth SMTP 설정 없이도 동작한다(모든 메일이 Resend 한 경로).

## 3. 메일이 안 올 때 Supabase 에서 확인하는 법

1. **그 이메일 계정에 아이디가 있는지** — SQL Editor:
   ```sql
   select u.email, u.email_confirmed_at is not null as confirmed,
          exists (select 1 from public.login_ids l where l.user_id = u.id) as has_login_id,
          (select string_agg(provider, ',') from auth.identities i where i.user_id = u.id) as providers
     from auth.users u where lower(u.email) = lower('여기에_이메일');
   ```
   - 결과가 없으면: 가입 안 된 이메일 → 메일을 보내지 않는 것이 정상.
   - `has_login_id = false`: 구글 등 간편 로그인이거나 아이디를 만들기 전 이메일 계정. **2026-11-11 배포 이후**에는 "아이디가 없어요" 안내 메일이 간다(그 전에는 아무 메일도 안 갔다 — 이번 "안 온다"의 가장 유력한 원인. 운영 DB 기준 회원 12명 중 아이디가 있는 계정은 2명).
2. **함수가 불렸는지·메일이 실패했는지** — 대시보드 > Edge Functions > `login-id` > **Logs**: `mail_failed` 검색. 상태코드 403/422 이면 Resend 쪽 문제(도메인 미인증·보내는 주소 불일치), 429 면 Resend 발송 한도. `too_many_attempts`는 10분 횟수 제한.
3. **Resend 쪽 발송 기록** — resend.com > Emails: 보낸 메일의 상태(Delivered/Bounced). Domains 에서 `duckchinso.com` 이 Verified 인지, `MAIL_FROM` 주소가 그 도메인인지.
4. **함수 비밀값** — 대시보드 > Edge Functions > Secrets 에 `RESEND_API_KEY`·`MAIL_FROM` 존재(2026-11-11 확인: 있음).
5. **받은편지함** — 스팸함·프로모션함.

## 4. 배포

| # | 내용 | 명령 |
| --- | --- | --- |
| 1 | DB: 세션 끊기 함수 | `npx supabase db push --linked` (마이그 32) |
| 2 | 서버 함수: 아이디 찾기 안내 메일·비밀번호 찾기·메일 실패 로그 | `npx supabase functions deploy login-id --no-verify-jwt` |
| 3 | 웹: 새 비밀번호 찾기 화면 | main 배포 |

순서: 1 → 2 → 3. 3 이 먼저 나가면 새 화면이 아직 없는 함수 동작(`reset_code`)을 불러 오류가 난다.

## 5. 하지 않는 것

- 휴대폰 본인인증: 전화번호를 받지 않는 서비스.
- 이메일을 잊은 경우: 문의로만. 운영자는 화면에서 이메일을 볼 수 없으므로(개인정보 비노출) 본인 확인 후 SQL Editor 로 처리.
- 캡차: 이 함수는 Supabase Auth 를 거치지 않아 Turnstile 이 적용되지 않는다. 대신 아이디·IP 횟수 제한 + 이메일 코드. 남용이 보이면 함수에서 Turnstile 토큰 서버 검증(`TURNSTILE_SECRET` 비밀값)을 추가.

# 운영자 권한 침해 경로 점검

점검일: 2026-11-11 · 질문: 일반 사용자(회원·비회원·비로그인)가 `is_admin()` 등 방어를 뚫고 운영자 화면을 보거나 운영자 기능을 실행할 수 있는가?

## 결론

**운영자 화면의 "틀"은 볼 수 있지만, 운영자 데이터를 읽거나 운영자 기능을 실행할 수는 없다.** 운영자 판단은 모두 서버(DB·Edge 함수)에서 하고, 화면 쪽 검사는 메뉴 표시용일 뿐이다. 점검 중 운영자 권한과 무관한 작은 정보 노출 2건을 찾아 고쳤다(5장).

## 1. 운영자는 어떻게 정해지나

- `public.admins` 표에 사용자 id 가 있으면 운영자. `is_admin()` = 회원(`is_member()`)이고 `admins`에 있음.
- `is_admin()`은 **로그인 토큰의 사용자 id(`auth.uid()`)만** 본다. 사용자가 직접 바꿀 수 있는 `user_metadata`·`app_metadata`·프로필 값은 권한 판단에 쓰지 않는다(전체 마이그레이션 검색으로 확인).
- 로그인 토큰은 Supabase 가 서명하므로 위조할 수 없다. service_role 키는 앱 번들에 없다(외부 점검 확인).

## 2. 시도할 수 있는 경로와 결과

| # | 경로 | 결과 | 근거 |
| --- | --- | --- | --- |
| 1 | 화면 검사 우회: 개발자 도구로 `isAdmin`을 true 로 바꾸거나 `/admin` 주소로 직접 이동 | **화면 틀만 보임, 데이터 없음** | `AdminGate`는 메뉴·경로 표시용. 운영자 화면의 모든 데이터는 아래 3~5번 경로로만 오고 거기서 막힌다 |
| 2 | 자기 자신을 `admins`에 넣기 | 불가 | 운영 DB 확인: `admins` 표에 앱 권한 없음 + RLS 켜짐(정책 없음). 운영자 수 1명 |
| 3 | 운영자 DB 함수 직접 호출 (`admin_users`, `admin_sanction`, `admin_delete_post` 등 20개) | 불가 (`forbidden`) | 운영 DB 확인: 일반 사용자가 실행할 수 있는 security definer 함수 중 운영자 기능 함수는 **모두 첫 줄에서 `require_admin()`/`is_admin()` 검사**. DB 테스트로 일반 회원 호출 시 forbidden 확인 |
| 4 | 운영 표 직접 읽기·쓰기 (공연 게시, 금칙어, 신고 목록, 제재, 운영 기록) | 불가 (`permission denied`) | 마이그 29로 표 권한 자체 회수. 운영 DB `has_table_privilege` 확인: 신고·문의는 넣기만, 금칙어·기획사·수집함·제재·운영 기록·admins 는 권한 없음 |
| 5 | 운영자 Edge 함수 호출 (`answer-inquiry`, `import-concert`) | 불가 (403) | 토큰으로 호출자를 확인한 뒤 서버 키로 `admins` 표를 다시 조회 |
| 6 | 수집 함수 호출 (`sync-concerts`, `sync-artists`) | 불가 (403) | 서버 키로 부른 요청만 허용(`isServiceCall`) |
| 7 | 내 프로필 `status`·`is_guest` 바꾸기 (정지 해제, 비회원→회원 위장) | 불가 | 운영 DB 확인: 두 칸에 UPDATE 권한 없음(칸 단위 권한) |
| 8 | 운영자가 아닌데 운영자 쓰기를 하는 security definer 함수 찾기 | 없음 | 운영 DB에서 "일반 사용자 실행 가능 + definer + 운영자 검사 없음" 함수 28개를 전수 확인: 모두 호출자 본인 데이터만 다룸(친구·메시지·글 수정·동의 등) |
| 9 | 비로그인(anon)으로 함수 호출 | 공연 공개용 `is_admin()`만 가능 | 마이그 30에서 회원 전용 함수 4개의 anon 실행 권한 회수 |
| 10 | 운영자 함수의 SQL 주입 | 해당 없음 | 모든 함수가 인자를 바인딩으로 받고, 동적 SQL(`execute format`)은 마이그레이션 안의 트리거 생성에만 있음 |
| 11 | 실시간(Realtime)으로 운영 데이터 엿보기 | 불가 | DB 변경 알림은 RLS 를 따른다. 구독 표는 `messages`·`friend_requests`뿐 |

## 3. 점검 방법

1. **시험 DB 전수 조사**: 마이그레이션 전체를 PGlite 에 올리고 `pg_proc`에서 security definer 함수마다 `authenticated`·`anon` 실행 권한과 운영자 검사 유무를 뽑았다. Supabase 의 "새 함수 기본 실행 권한" 설정을 켠 최악 조건으로도 다시 돌렸다 → 차이는 무해한 `require_active_member()` 1개.
2. **운영 DB 읽기 전용 조회**(`supabase db query --read-only`): 같은 함수 조건, 표별 `has_table_privilege('authenticated', …)`, `profiles.status`/`is_guest` 칸 권한, 운영자 수, 모든 표 RLS 켜짐 확인.
3. **코드 확인**: Edge 함수 인가 순서, 화면 운영자 검사(`AdminGate`), 메타데이터 사용처.
4. **DB 테스트**(`pnpm test`): 일반 회원·비회원·정지 계정으로 운영자 함수·운영 표 접근이 거절되는 단언문.

## 4. 남는 점 (위험 낮음)

- **운영자 화면 코드가 공개 번들에 들어 있다.** 화면 구성·함수 이름은 누구나 볼 수 있지만 비밀값은 없고 실행은 서버가 막는다. 숨기려면 운영자 화면을 별도 빌드로 분리해야 하는데, 얻는 것에 비해 비용이 커서 하지 않는다.
- **운영자 계정 탈취가 가장 현실적인 위험**이다. 운영자 계정은 아이디 로그인 + 캡차만 있다. 권장: 운영자 계정에 Supabase MFA(TOTP)를 켜고 `is_admin()`에 `auth.jwt() ->> 'aal' = 'aal2'` 조건을 더한다(운영자 로그인 화면에 OTP 입력 추가 필요 — 별도 작업).
- 운영자 변경은 운영 기록(`admin_audit_log`)에 남으므로, 탈취돼도 사후 추적은 된다.

| 문제 | 영향 | 조치 |
| --- | --- | --- |
| `is_blocked_between(a, b)`를 아무 두 사람으로 부를 수 있었다 | 회원이 남의 차단 관계(누가 누구를 차단했는지)를 알아낼 수 있음. `blocks` 표는 본인 것만 읽히는데 함수로 우회 | 호출자가 둘 중 하나일 때만 답하도록. 모든 정책·함수가 (본인, 상대)로 부르므로 동작은 같다 |
